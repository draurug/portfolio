Battleship, with the rules kept out of the UI

A Qt Widgets Battleship game against a simple computer opponent. The exercise was the seam between rules and interface. The game rules are 456 lines that include no Qt header, and the widgets hold no copy of the board.

Gameplay

Two ten-by-ten grids side by side. The player places a fleet of ten ships by hand, the computer places its own at random, and the two sides then alternate shots until one fleet is gone. It implements the Soviet variant of the rules. In practice that means a fleet of one four-cell ship, two threes, three twos and four singles, and ships that may not touch even diagonally.

That adjacency rule is the fiddliest piece of game logic. Board::hasAdjacentShip walks all eight neighbours of every cell a proposed ship would occupy, and canPlaceShip refuses the placement if any of them is already occupied. A permissive error here produces a board that looks fine and plays wrong, so it belongs behind a testable interface.

The separation

I started the project to build a Qt application where deleting the UI would leave the rules intact. Three classes carry the game.

  • Ship: size, origin, orientation, hit count. It can enumerate the cells it covers and say whether it is sunk.
  • Board: a grid of CellState plus the ships on it. It owns placement legality, placement, and resolving a shot into hit/miss/sunk. It does not know whose board it is.
  • Game: two boards, the fleet list, a GameState enum, and the computer's targeting state. It is the only thing that decides whose turn it is.

Between them those headers include <vector>, <memory>, <random> and <chrono>. No QObject, no signals, no Q_OBJECT macro. They compile with a bare g++ and no Qt on the include path. That is the property I wanted, because it forces every rule to live in one place. I have no plan to port the front end.

The widgets never hold state the model does not already have. There is one copy of the board, so there is one place to fix it.

BoardWidget is the whole of the view. It holds a non-owning Board* and paints whatever that board currently says: paintEvent reads getCellState() and getShips() and draws the result. It has no grid of its own and no opinion about whether a move is legal. On a click it converts pixel coordinates into a row and column and emits cellClicked(row, col), and that is the entire input path.

The same class draws both grids. Hiding the opponent's fleet is a display flag, setShowShips(false), on the same model. MainWindow owns the Game, wires the two widgets' signals to slots that call into it, and reads getState() back to decide what the status line says. The flow runs one way: click, slot, game method, state change, repaint from the model.

The seam has a flaw. MainWindow passes &game_->getPlayerBoard() to the widget, so the view holds a raw pointer into the Game's interior, and Game exposes both boards non-const. It is safe, since the game outlives the widgets. It is still a wider interface than the widget needs. The right signature was const Board&.

Building against two Qt majors

CMake tries Qt6 first and falls back to Qt5:

find_package(Qt6 COMPONENTS Core Widgets QUIET)
if(Qt6_FOUND)
    set(QT_VERSION_MAJOR 6)
else()
    find_package(Qt5 REQUIRED COMPONENTS Core Widgets)
    set(QT_VERSION_MAJOR 5)
endif()

Only the link line differs. Nothing in the source is version-specific, mostly because the code uses a small and old part of the API. It touches QPainter, layouts, QTimer::singleShot and a handful of widgets, all spelled the same way in both versions.

Caveat: the Qt6 path is the one I build and run, verified on CMake 4.3, GCC 16.1 and Qt 6.11. The Qt5 branch is written, in the older and better-trodden spelling, but I have not compiled it. The machine had Qt5's runtime libraries without the development package. Calling it "tested on both" would be a guess.

Unfinished work

The computer opponent fires at random until it hits, then works through the four orthogonal neighbours of that hit before going back to random fire. It does not infer a ship's orientation from two hits in a line. It does not rule out the diagonals around a sunk ship, even though the placement rules guarantee they are empty. Both are the obvious next things to add.

BoardWidget also carries a placement-preview method and hover tracking that nothing calls. MainWindow only ever clears the preview and never sets it. That is dead code and should be wired up or deleted. There are also no tests. The domain layer is shaped so they would be easy to write, which I have not done.
