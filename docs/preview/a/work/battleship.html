Battleship, with the rules kept out of the UI

A Qt Widgets Battleship game against a simple computer opponent. The point of the exercise was the seam: the game rules are 456 lines that do not include a single Qt header, and the widgets hold no copy of the board.

What it does

Two ten-by-ten grids side by side. You place a fleet of ten ships by hand, the computer places its own at random, and then the two sides alternate shots until one fleet is gone. It implements the Soviet variant of the rules rather than the boxed-game one, which mainly means the fleet is one four-cell ship, two threes, three twos and four singles, and that ships may not touch even diagonally.

That adjacency rule is the only genuinely fiddly piece of game logic. Board::hasAdjacentShip walks all eight neighbours of every cell a proposed ship would occupy, and canPlaceShip refuses the placement if any of them is already occupied. Getting it wrong in the permissive direction produces a board that looks fine and plays wrong, which is exactly the kind of thing worth having behind a testable interface.

The separation

The whole project exists because I wanted to build a Qt application where deleting the UI would not touch the rules. Three classes carry the game:

  • Ship — size, origin, orientation, hit count. It can enumerate the cells it covers and say whether it is sunk.
  • Board — a grid of CellState plus the ships on it. It owns placement legality, placement, and resolving a shot into hit/miss/sunk. It does not know whose board it is.
  • Game — two boards, the fleet list, a GameState enum, and the computer's targeting state. It is the only thing that decides whose turn it is.

Between them those headers include <vector>, <memory>, <random> and <chrono>. No QObject, no signals, no Q_OBJECT macro. They compile with a bare g++ and no Qt on the include path, which is the property I actually wanted — not because I plan to port the front end, but because it forces every rule to live in one place.

The widgets never hold state the model does not already have. If the two ever disagree, there is only one of them to fix.

BoardWidget is the whole of the view. It holds a non-owning Board* and paints whatever that board currently says: paintEvent reads getCellState() and getShips() and draws the result. It has no grid of its own and no opinion about whether a move is legal. On a click it converts pixel coordinates into a row and column and emits cellClicked(row, col), and that is the entire input path.

The same class draws both grids. Hiding the opponent's fleet is setShowShips(false) — a display flag, not a second model. MainWindow owns the Game, wires the two widgets' signals to slots that call into it, and reads getState() back to decide what the status line says. So the flow runs one way: click, slot, game method, state change, repaint from the model.

The seam is not spotless. MainWindow passes &game_->getPlayerBoard() to the widget, so the view holds a raw pointer into the Game's interior, and Game exposes both boards non-const. It is safe because the game outlives the widgets, but it is a wider interface than the widget needs, and a const Board& would have been the honest signature.

Building against two Qt majors

CMake tries Qt6 first and falls back to Qt5:

find_package(Qt6 COMPONENTS Core Widgets QUIET)
if(Qt6_FOUND)
    set(QT_VERSION_MAJOR 6)
else()
    find_package(Qt5 REQUIRED COMPONENTS Core Widgets)
    set(QT_VERSION_MAJOR 5)
endif()

Only the link line differs; nothing in the source is version-specific, which is mostly a consequence of using a small, old part of the API. The application code touches QPainter, layouts, QTimer::singleShot and a handful of widgets, and all of that is spelled the same way in both.

Honest caveat: the Qt6 path is what I actually build and run — verified on CMake 4.3, GCC 16.1 and Qt 6.11. The Qt5 branch is written and is the older, better-trodden spelling, but I have not compiled it, because the machine had Qt5's runtime libraries without the development package. Calling it "tested on both" would be a guess.

What is not finished

The computer opponent fires at random until it hits, then works through the four orthogonal neighbours of that hit before going back to random fire. It does not infer a ship's orientation from two hits in a line, and it does not rule out the diagonals around a sunk ship even though the placement rules guarantee they are empty. It is beatable, and it is meant to be, but it is the obvious next thing.

BoardWidget also carries a placement-preview method and hover tracking that nothing calls — MainWindow only ever clears the preview, never sets it. It is dead code and should either be wired up or deleted. And there are no tests: the domain layer is shaped so they would be easy to write, which is not the same as having written them.
