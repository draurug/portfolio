Networked tic-tac-toe client in Qt

A Qt Widgets client for a networked tic-tac-toe. Most of the work sits in the handshake that takes two connected strangers to a shared, consistent game state over a protocol with no turn token and no game-over message.

Authorship

The client is mine: the UI, the dialogs, the player list, and Logic, the state machine between them and the socket. The server, the TCP plumbing and the protocol constants come from a course repository by another author. I keep them as a GPL-3.0 submodule so the boundary stays visible. The 942 lines in the metric above are theirs, counted separately.

The protocol

Plain ASCII, comma-separated fields, semicolon-terminated. Fourteen message types. The server is a relay and a registry. It tracks who is online and busy and forwards invitations and moves. It arbitrates nothing about the game. Framing is the first problem: several messages can land in one TCP read, so the reader splits on ; instead of assuming one message per packet.

The messages that carry the handshake.
MessageDirectionMeaning
[PlayerList]S→CName/busy pairs; empty busy field is free
[Invite]C→SAsk to play against someone
[Invitation]S→CAn invitation arrived
[AcceptInvitation]C→SAccept
[InvitationAccepted]S→CThe invitation was accepted
[Step] / [OnStep]bothA move, as symbol plus coordinates

The invite handshake and role assignment

A client walks through cst_initial → cst_handshaking → cst_waiting_user_choice, and from there either into cst_inviting or cst_invite_responding, and on success into cst_gaming.

  A                      server                      B
  |-- [Invite],B ------>|                             |
  |                     |-- [Invitation],A --------->|  modal dialog
  |                     |<--- [AcceptInvitation],A --|  B accepts
  |<- [InvitationAccepted],B                          |
  |   A := O, waits     |               B := X, moves first

Roles are never negotiated on the wire. No message assigns a symbol. The convention is positional: whoever accepts plays X and moves first. Each client sets its own m_playerRoleX locally when it learns the outcome, from opposite branches of the code.

That saves a round trip. It is also fragile in a specific way: if either side takes the wrong branch, the two clients disagree silently and the boards drift apart while everything still looks fine. The step handler now rejects any incoming move claiming the symbol this client believes is its own, so the corruption surfaces as a visible refusal and can be found.

Turn synchronisation and game-over detection

There is no turn token. Each client holds a single bool m_makingStep: true on the accepting side at game start, cleared when the client sends a move, set when one arrives. Everything is relayed through one server over an ordered TCP stream, so the two flags stay complementary with no further coordination. Each client keeps its own replica of the board.

The protocol reserves [GameEnded] and [GameIsOver]. The client library never sends them, and handles the latter with an empty branch. Nothing detected a win.

So the game had no ending. I resolved it locally instead of extending someone else's protocol. Both clients hold the full grid and apply the same moves, so both reach the same verdict with no round trip. On a win or draw the client reports the result, sends [CloseGame], clears the board and returns to the player list. The replicated state is what makes that legitimate: the verdict is a pure function of a grid both sides already agree on.

Bugs fixed

The client compiled but was not playable. The click handler bounds-checked a three-by-three array with x <= 3, so a click in the widget's margin wrote past the end of it. It consulted neither the state machine nor the turn flag, which allowed marking cells before a game started and moving twice in a row. The grid was never cleared between games. The "waiting for response" dialog was heap-allocated, never freed, and dereferenced through a stale pointer after a cancel. Scene declared a scoreboard that was never constructed, with methods that dereferenced it.

Verification

A headless test plays complete games between two real clients against the real server, wired into ctest. It builds two MainWindows, each with its own Logic, exactly as main.cpp wires the shipped app, and starts the server as a child process. Moves go in through QTest::mouseClick on the real board, invitations are answered by accepting the real modal dialog, and results are read out of the real message boxes. Nothing is stubbed.

It covers registration and the player table, the invite button through to acceptance, role assignment, a game played to a win with both clients asserted to detect it and agree, an out-of-turn click asserted to change nothing, the board clearing afterwards, a declined invitation, and a draw.

That needed one change to the application. MainWindow pulled its Logic from a process-wide singleton in ten places, so two clients could not coexist in one process. Injecting Logic& made it drivable.

Writing it also turned up a shutdown bug. closeSocket() only calls close(), which does not wake a thread already blocked in read(), so joining the reader hangs forever. The application never notices, because it never destroys its Logic. It leaks the thread at exit.

Reverting the turn guard makes the out-of-turn assertion fail. Stubbing out the win check makes the game-over assertion fail. The tests fail when the code is wrong.

Still not covered: Qt5, the untested branch of the build fallback; reconnection and a partner quitting mid-game, neither of which has defined behaviour yet; the settings dialog, which the tests bypass; anything beyond two clients on loopback.
