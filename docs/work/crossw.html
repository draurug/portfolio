CrossW: crosswords where the theme is in the clue

A crossword site. The theme of a puzzle is carried by its clues, which is what makes the content problem tractable: a themed crossword can be filled with ordinary words.

The site itself is in Russian. The packs are built from Russian-language books and the clues are written in Russian. This page describing it is in English.

The idea

Filling a grid about The Master and Margarita with words from the novel fails immediately. A themed vocabulary is mostly proper nouns and long words. A grid is mostly three-, four- and five-letter slots, and more than half of them will take nothing recognisably thematic. The usual fix is to give up on most of them: a handful of on-topic answers, the rest filled with whatever fits.

The theme is a property of the clue. ТРАМВАЙ (tram) is an ordinary word. The clue "the transport that beheaded Berlioz" makes it belong to Bulgakov.

That moves the constraint off the grid and into the writing, where it is tractable. Any word the fill needs can be pulled into the theme if the book gives it a moment. The generator knows which entries in a pack have a topical clue available and prefers them when scoring a candidate grid. The proportion of genuinely on-theme clues then becomes a number I can measure and optimise.

Four packs exist so far, each drawn from one book: The Master and Margarita, Sherlock Holmes, The Twelve Chairs, and the Emelya folk tale. A pack holds 175 to 329 entries, 1,103 in total across 59 categories. An entry is an answer with two clues: one topical, one plain dictionary. Clues that give away the ending are marked hard and withheld from the easy levels. 168 topical clues carry the exact line from the book as a further hint. Each pack generates eight levels of increasing size and difficulty. Words are spent: once an answer is used in a level of a theme it leaves the pool entirely, so later levels in that theme never recycle it.

The deployed site

The deployed build opens on a list. It carries a title, the line "Определения тут не из словаря, а из книг" (the clues here come from books, not dictionaries), four starter puzzles marked Easy at 11×11 with their word counts, and four theme cards with a one-line description of each book. The footer counts what is live: 32 crosswords and 565 words, which is all eight levels of every theme. Clicking a puzzle opens the grid and the numbered clue list. Both are keyboard-driven, which follows from the "designed for desktop" decision stated up front. There is no mobile layout and no arrow-word variant.

A sources page carries the attribution. The grid filler draws its vocabulary from OpenCorpora (CC BY-SA 4.0) and drops rare words by wordfreq frequency (Apache 2.0). Book texts are not copied or stored: a topical clue restates a fact in its own words, and every entry records which book the fact comes from.

Structure

The source is four layers with one rule about the direction of dependency.

  • src/core/: the grid model, numbering, and content rules. Pure functions, no state.
  • src/engine/: game state: cursor, current entry, the effect of typing a letter. Also pure functions, and free of React, so the rules of the game can be tested without rendering anything.
  • src/components/ and src/hooks/: the interface. It owns no game logic; every state transition is a call into the engine.
  • tools/: the generator, the content compiler and the validator. This is the only directory allowed to import node:fs.

That last restriction is what makes the static export work. Filesystem access is confined to the build-time tools, so everything under src/ runs in a browser unmodified, and next build emits a folder of static files that Cloudflare Workers serves with no runtime. It also keeps the 75 tests cheap to write: pure functions in, expected values out, no DOM and no mocked filesystem.

Content is split the same way. content/packs/ holds the word lists with their clues. content/puzzles/ holds the generated grids as real letters, in human-readable JSON, committed, so a change to a puzzle shows up as a legible diff and can be reviewed by eye. A validator (npm run validate) gates content on hard errors. A second pass (npm run review) reports what only looks suspicious and needs a human judgement.

Answer obfuscation

The compile step rewrites those readable grids so that devtools give nothing away. A compiled puzzle is a flat array of cell codes: -1 for a block, 0 for an empty cell, a positive integer for a numbered entry start. Alongside it is a list of entries giving each one's direction, its cell indices and its clue text. No letters appear anywhere in it. The solution goes out in a separate <id>.sol file, where the answer string is permuted by a key, so the file reads as 80713c73fb35c0db… instead of as words.

The bar this clears is view source. Anyone determined can read the client bundle, find the key and undo the permutation. The threat model is the idly curious solver, and for that the bar only has to sit above one keypress. The repo calls this obfuscation and says so plainly.

Deliberate omissions

No mobile layout, no arrow-word variant, no monorepo, no schema validation library, no CI, no browser-level end-to-end tests. I considered each and left it out; with one developer and a static site they would be scaffolding around scaffolding. What did get built is a content validator, a review pass and 75 tests on the pure layers. Those catch the failures this project actually has, which are almost all content failures.
