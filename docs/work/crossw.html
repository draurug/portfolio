CrossW: crosswords where the theme is in the clue

A crossword site built around one constraint that turned out to solve the whole content problem — a themed crossword does not need themed words, it needs themed clues.

The site itself is in Russian — the packs are built from Russian-language books and the clues are written in Russian. This page describing it is in English.

The idea

Try to build a crossword about The Master and Margarita by filling the grid with words from the novel and you fail immediately. A themed vocabulary is mostly proper nouns and long words; a grid is mostly three-, four- and five-letter slots, and more than half of them will not accept anything recognisably thematic. Every themed crossword you have ever seen solves this by giving up — a handful of on-topic answers and the rest filled with whatever fits.

The theme is a property of the clue, not of the word. ТРАМВАЙ (tram) is an ordinary word. "The transport that beheaded Berlioz" makes it belong to Bulgakov.

Once you accept that, the constraint moves off the grid and into the writing, where it is tractable. Any word the fill needs can be pulled into the theme if the book gives it a moment. The generator knows which entries in a pack have a topical clue available and prefers them when scoring a candidate grid, so the proportion of genuinely on-theme clues becomes a thing you can measure and optimise rather than hope for.

Four packs exist so far, each drawn from one book: The Master and Margarita, Sherlock Holmes, The Twelve Chairs, and the Emelya folk tale. A pack is 150–200 entries — an answer with one or more clues, tagged by kind, some marked hard for connoisseurs. Each pack generates eight levels of increasing size and difficulty, and words are spent: once an answer is used in a level of a theme it is removed from the pool rather than pushed to the back of the queue, so later levels in a theme do not recycle the same answers.

What a visitor sees

The deployed build opens on a list rather than a grid: a title, the line "Определения тут не из словаря, а из книг" (the clues here come from books, not dictionaries), four starter puzzles marked Easy at 11×11 with their word counts, and four theme cards each carrying a one-line description of the book. The footer counts what is live — currently 12 crosswords and 272 words, which is three levels per theme rather than the eight the generator produces; the rest are built but not yet deployed. Clicking a puzzle opens the grid and the numbered clue list, keyboard-driven, which is the point of the "designed for desktop" decision stated up front: no mobile layout, no arrow-word variant.

How it is put together

The source is four layers with one rule about the direction of dependency:

  • src/core/ — the grid model, numbering, and content rules. Pure functions, no state.
  • src/engine/ — game state: cursor, current entry, what happens when you type a letter. Also pure functions, and deliberately free of React, so the rules of the game can be tested without rendering anything.
  • src/components/ and src/hooks/ — the interface. It owns no game logic; every state transition is a call into the engine.
  • tools/ — the generator, the content compiler and the validator. This is the only directory allowed to import node:fs.

That last restriction is what makes the static export work at all. Because filesystem access is confined to the build-time tools, everything under src/ can run in a browser without qualification, and next build emits a folder of static files that Cloudflare Workers serves with no runtime at all. It is also why the 75 tests are quick to write: pure functions in, expected values out, no DOM, no mocking of a filesystem.

Content is also split by layer. content/packs/ holds the word lists with their clues and content/puzzles/ holds the generated grids as real letters — human-readable JSON, committed, so a change to a puzzle shows up as a legible diff and can be reviewed by eye. A separate validator (npm run validate) gates content on hard errors, and a second pass (npm run review) reports things that merely look suspicious and need a human's judgement.

Answers the browser cannot read

The compile step rewrites those readable grids into something a solver cannot cheat from by opening devtools. A compiled puzzle is a flat array of cell codes — -1 for a block, 0 for an empty cell, a positive integer for a numbered entry start — plus a list of entries giving each one's direction, its cell indices and its clue text. No letters appear anywhere in it. The solution goes out in a separate <id>.sol file, where the answer string is permuted by a key, so the file reads as 80713c73fb35c0db… rather than as words.

This is worth being precise about: it is obfuscation against view source, not cryptography. Anyone determined can read the client bundle, find the key and undo the permutation. The threat model is the solver who is idly curious, and for that the bar only needs to be higher than one keypress. Saying so in the repo rather than calling it encryption seemed like the honest option.

What is deliberately missing

No mobile layout, no arrow-word variant, no monorepo, no schema validation library, no CI, no browser-level end-to-end tests. Each of those was considered and left out: with one developer and a static site, they would be scaffolding around scaffolding. The things that did get built — a content validator, a review pass, 75 tests on the pure layers — are the ones that catch the failures this project actually has, which are almost all content failures rather than code failures.
