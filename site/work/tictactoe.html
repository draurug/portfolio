Getting two clients to agree who is X

A Qt Widgets client for a networked tic-tac-toe. The game is three-in-a-row; the actual work is the handshake that takes two connected strangers to a shared, consistent game state over a protocol with no turn token and no game-over message.

What is mine and what is not

Worth stating first. The client is mine: the UI, the dialogs, the player list, and Logic, the state machine between them and the socket. The server, the TCP plumbing and the protocol constants are not — they come from a course repository by another author, kept as a GPL-3.0 git submodule so the boundary stays visible rather than quietly absorbed. My Logic derives from their tic_tac::TicTacClient. The 942 lines in the metric above are theirs, counted separately for that reason.

The protocol

Plain ASCII, comma-separated fields, each message terminated by a semicolon. Fourteen message types, split by prefix into client-to-server and server-to-client. The server is a relay and a registry: it tracks who is online and who is busy and forwards invitations and moves. It arbitrates nothing about the game itself. Framing bites first — several messages can land in one TCP read, so the reader splits on ; rather than assuming one message per packet.

The messages that carry the handshake.
MessageDirectionMeaning
HiS→CGreeting; client must answer with a name
[PlayerName]C→SRegister under this name
[PlayerList]S→CName/busy pairs; empty busy field means free
[Invite]C→SAsk to play against someone
[Invitation]S→CYou have been invited
[AcceptInvitation]C→SAccept
[InvitationAccepted]S→CYour invitation was accepted
[Step] / [OnStep]bothA move, as symbol plus coordinates

The invite handshake and role assignment

A client walks through cst_initial → cst_handshaking → cst_waiting_user_choice, and from there either into cst_inviting or cst_invite_responding, and on success into cst_gaming.

  A                      server                      B
  |-- [Invite],B ------>|                             |
  |                     |-- [Invitation],A --------->|  modal dialog
  |                     |<--- [AcceptInvitation],A --|  B accepts
  |<- [InvitationAccepted],B                          |
  |   A := O, waits     |               B := X, moves first

The part I find interesting is that roles are never negotiated on the wire. There is no message that says "you are X". The convention is positional — whoever accepts plays X and moves first — and each client sets its own m_playerRoleX locally at the moment it learns the outcome, from opposite branches of the code.

That works, and it costs a round trip less than negotiating. It is also fragile in a specific way: if either side ever takes the wrong branch, the two clients disagree silently and both boards drift apart while everything still looks fine. So I added a check in the step handler that rejects any incoming move claiming the symbol this client believes is its own. It cannot repair the disagreement, but it turns silent corruption into a visible refusal, which is the difference between a bug you can find and one you cannot.

Turn synchronisation, and the missing end of the game

There is no turn token in the protocol. Each client holds a single bool m_makingStep: set true on the accepting side at game start and false on the inviting side, cleared when you send your own move, set when a move arrives. Because everything is relayed through one server over an ordered TCP stream, the two flags stay complementary without any further coordination. The board is replicated rather than shared — both clients apply the same moves to their own grid.

The protocol reserves [GameEnded] and [GameIsOver]. The client library never sends them, and handles the latter with an empty branch. Nothing detected a win.

So the game had no ending. I resolved it locally instead of extending someone else's protocol: because both clients hold the full grid and apply the same moves, both reach the same verdict with no round trip. On a win or draw the client reports the result, sends [CloseGame] so the server stops listing it as busy, clears the board and returns to the player list. Replicated state is what makes that legitimate — the conclusion is a pure function of a grid both sides already agree on.

What I had to fix

The client compiled but was not playable. The click handler bounds-checked a three-by-three array with x <= 3, so a click in the widget's margin wrote past the end of it. It checked neither the state machine nor whose turn it was, so you could mark cells before a game started and move twice in a row. The grid was never cleared between games. The "waiting for response" dialog was heap-allocated, never freed, and dereferenced through a stale pointer after a cancel. And Scene declared a scoreboard and reset buttons that were never constructed, with methods that dereferenced them — unreachable in the networked flow, but a crash waiting for whoever wired them up.

On the build side, find_package was asking Qt for a component called Boost, and the Boost lookup relied on CMake's FindBoost, removed in CMake 4.0.

How far it is verified

I wrote a raw-socket probe in Python that drives the wire protocol against the real server — register, invite, accept, a move each way — and it passes. Two real clients started headless both connect and register cleanly.

What I have not verified is a full two-client game through the GUI. Accepting an invitation goes through a modal dialog and every move is a widget click, so driving one headlessly needs a UI-automation harness this repo does not have. The invite, turn and game-over logic is implemented and compiles, and the protocol underneath it is tested, but the combination has only been reasoned about, not exercised end to end.
